# フロントエンドの設計を決める

project の init（context の後）・update（「フロントエンドの設計を決める・見直す」）と dev の Approach（画面を作る・変えるのに設計が無いとき）が、その手順の指示で Read する。決めたものは `docs/context/frontend.md` に書き、dev の Approach と Review が守らせる。合意を得る場所（ゲート）と、ファイルを書くか（dev は Plan の commit に入れる）は呼ぶ側が示す。

1. **フロントエンドがあるか**：コード（`package.json` の依存に react・vue・svelte・next・nuxt・astro など、`apps/web` のようなディレクトリ）か、作るものの説明（`docs/context/overview.md`・チケット）に画面があるかを見る。どちらも無ければ、何もせずに呼ぶ側に戻る。モノレポなら、フロントエンドのパッケージを並べ、どれを決めるか尋ねる（全部でもよい）。
2. **今の形**：決めるパッケージに画面のコードが既にあれば、今の tree（主なディレクトリまで）を示し、「今の形を記録する」か「目指す形を決める（移す作業はチケットにする）」かを尋ねる。散らかった今の形を、そのまま正解にしないため。「記録する」なら、手順 3 は今の形を書き起こして確かめるだけにする。`docs/context/frontend.md` が既にあれば（update の見直し）、今の内容を示し、変える軸だけを尋ねる。
3. **軸ごとに選んでもらう**：作るもの（`overview.md`・チケット・技術スタック）を見て、軸ごとに AskUserQuestion で尋ねる（1 問 1 軸、1 回に 4 問まで）。選択肢は推奨 3 つ（それぞれに、この作るものに合う理由。最も合うものを先頭に「（推奨）」）で、自由に書く Other は自動で付く。案は案として示し、決めるのはユーザー：
   - **デザインパターン**（必ず尋ねる）：コンポーネントとディレクトリの構成（例：Atomic Design・Container／Presentational・機能単位（feature-sliced など））。各選択肢の `preview` に tree の例を付ける（名前だけだと解釈が人によって違うため）。
   - **メインカラー・サブカラー**（トークンのファイルがまだ無いときだけ）：作るものの雰囲気に合う組み合わせを 3 つ、`preview` に色の値（`#rrggbb`）で示す。既にトークンのファイル（CSS 変数・Tailwind の theme など）があれば尋ねず、その場所を書く。
   - **状態管理・データの取り方**（作るものに要るときだけ。例：サーバーの状態は TanStack Query、画面の状態は Zustand）。技術スタックで決まっていれば尋ねない。
4. **下書きを示す**：`<plugin>/templates/docs/frontend.md` を Read し、その先頭のコメントの決まりに従って、選んだものから下書きを作る。デザインパターンの節には選んだ tree を書き、置き場所と依存の規則を、そのパターンの一般的な形から 3〜6 行で書き起こす（この規則は案なので、示して確かめる）。Other で書かれたものは、書かれたとおりに使い、足りない所（tree・規則）を尋ねる。全体を示して、呼ぶ側のゲートで合意を得る。
5. **書く**：合意を得たら、呼ぶ側の指示に従って `docs/context/frontend.md` に書く（既にあれば差分を示してから書き換える）。dev では、この場では書かず、Plan の commit 一覧に入れて Implement で書く。
