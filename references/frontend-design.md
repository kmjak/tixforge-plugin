# フロントエンドの設計を決める

project の init（context の後）・update（「フロントエンドの設計を決める・見直す」）と dev の Approach（`frontend.md` はあるのに、触るパッケージの節が無いとき）が、その手順の指示で Read する。決めたものは `docs/context/frontend.md` に書き、dev の Approach と Review が守らせる。合意を得る場所（ゲート）と、ファイルを書くか（dev は書かずに `## Approach` に残す）は呼ぶ側が示す。

1. **フロントエンドがあるか**：コード（`package.json` の依存に react・vue・svelte・next・nuxt・astro など、`apps/web` のようなディレクトリ）か、作るものの説明（`docs/context/overview.md`・チケット・渡された文）に画面があるかを見る。どちらも無ければ、見つからなかったことを伝え、画面を作る予定があるか尋ねる（無ければ呼ぶ側に戻る。あれば、コードの無いパッケージとして続ける）。モノレポなら、フロントエンドのパッケージを並べ、どれを決めるか尋ねる（全部でもよい。4 つを超えるなら選択肢にせず、文で答えてもらう）。dev から呼ばれたときは、触るパッケージに決まっているので尋ねない。
2. **今決めるか**（init だけ。update と dev は呼ぶ側で決まっている）：「今決める」「後で決める（`/tixforge:project update` で決められる。dev は決まるまで近くの既存のコードに合わせる）」を尋ねる。後でなら、呼ぶ側に戻る（「後で」は記録しないので、init を再実行すると、`frontend.md` が無ければまた尋ねる）。
3. **今の形**：
   - `docs/context/frontend.md` に、決めるパッケージの `## Path:` の節が既にあれば（update の見直し）、今の内容を示し、変える軸だけを尋ねる。節の無いパッケージは、新しく決める。
   - 決めるパッケージに画面のコードが既にあれば、今の tree（主なディレクトリまで）を示し、「今の形を記録する」か「目指す形を決める」かを尋ねる（散らかった今の形を、そのまま正解にしないため）。「記録する」なら、手順 4 のデザインパターンは今の形を書き起こして確かめるだけにする。「目指す形を決める」なら、今の形のままのディレクトリを `Legacy:` の行に並べる（移すまで規則の対象外。移す作業は、終わった後に `/tixforge:ticket create` で作れることを案内する）。
4. **軸ごとに選んでもらう**：作るもの（`overview.md`・チケット・技術スタック）を見て、軸ごとに AskUserQuestion で尋ねる（1 問 1 軸、1 回に 4 問まで）。選択肢は推奨 3 つ（それぞれに、この作るものに合う理由。最も合うものを先頭に「（推奨）」）で、自由に書く Other は自動で付く。案は案として示し、決めるのはユーザー。`overview.md`・渡された文・技術スタックで既に決まっている軸は、選ばせずに示して確かめるだけにする：
   - **デザインパターン**（必ず決める）：コンポーネントとディレクトリの構成（例：Atomic Design・Container／Presentational・機能単位（feature-sliced など））。各選択肢の `preview` に tree の例を付ける（名前だけだと解釈が人によって違うため）。
   - **メインカラー・サブカラー**（トークンのファイルがまだ無いときだけ）：作るものの雰囲気に合う組み合わせを 3 つ、`preview` に色の値（`#rrggbb`）で示す。既存のコードで直書きの色が多く使われていれば、それを 1 つ目の案にする（「記録する」なら、それを示して確かめるだけにする）。トークンのファイル（CSS 変数・Tailwind の theme など）が既にあれば尋ねず、その場所を書く。トークンのファイルがあるのに色を変えたいと言われたら、色の正本はそのファイルなので、それを直すチケットで変えるよう伝える（ここでは変えない）。
   - **状態管理・データの取り方**（作るものに要るときだけ。例：サーバーの状態は TanStack Query、画面の状態は Zustand）。
5. **下書きを示す**：`<plugin>/templates/docs/frontend.md` を Read し、その先頭のコメントの決まりに従って、選んだものから下書きを作る。デザインパターンの節には選んだ tree を書き、置き場所と依存の規則を、そのパターンの一般的な形から 3〜6 行で書き起こす（この規則は案なので、示して確かめる）。Other で書かれたものは、書かれたとおりに使い、足りない所（tree・規則）を尋ねる。全体を示して、呼ぶ側のゲートで合意を得る。
6. **残す**：
   - init・update：合意を得たら `docs/context/frontend.md` に書く（既にあれば差分を示してから書き換える）。
   - dev：ここでは書かない。合意した下書きの全文（色の初期値を含む）を `## Approach` に書き、`frontend.md` の作成・更新を Plan の commit 一覧に入れる。Implement はそれを写す（compact の後も同じものを書き、reviewer が合意と照らせるようにするため）。
