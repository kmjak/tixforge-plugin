# tixforge 共通規約

`project`・`ticket`・`dev` の 3 つのスキルに共通する規約。

手順ファイルの中の表記：

- `<plugin>` — plugin のディレクトリ（上の「置き場所」に実際のパスがある）
- `<scripts>` — `<plugin>/scripts`。スクリプトは `bash <scripts>/<名前>.sh …` で実行する
- `references/<名前>.md` — `<plugin>/references/<名前>.md`

**会話の言語**：ユーザーへの質問・説明・選択肢（AskUserQuestion の文言を含む）は、個人の言語（「現在の状態」の「この人が使う値」の `language`）で書く。設定が無いとき（init で言語を決める前を含む）は日本語。ユーザーが明らかに別の言語の文章で書いてきたときだけ、その言語に合わせる。スラッシュコマンドや選択肢の回答だけでは言語を判断しない（英語に切り替えない）。

**会話が要約された後**は、続ける前に、今の手順ファイルと（dev なら）`.tixforge/<ticket-id>/state.md` を Read し直す。要約には手順の細部が残らないため。

## 共通規約

チケット id を全ての基点にする：チケットと状態のフォルダ名・ブランチ接頭辞。

**チケット id の形式：** チケットは GitHub issue で、id は `GT-<issue 番号>`。番号は 6 桁に 0 埋めする（`GT-000123` は issue #123）。番号が 6 桁を超えたら 0 埋めせずにそのまま使う。issue が正本（`references/github/`）で、番号は create で issue を作って得る。

**v2 からの移行**：「現在の状態」に「移行が要る」があれば、`/tixforge:project update` のとき以外は、その内容を伝えて止まる。

**チケットの操作**：手順はチケットへの操作を次の名前で呼ぶ。名前で呼ばれた操作を行う前に、表の手順ファイルを（このセッションでまだ読んでいなければ）Read し、その手順で行う。

| 操作 | すること | 手順 |
|------|----------|------|
| 作る | チケットを作って id を決める・GitHub 上で作られたものを取り込む | `references/github/create.md` |
| 取ってくる | 手元のコピーを作り直し、変わったかとチケットの状態を返す | `references/github/fetch.md` |
| 探す | 似たチケット・着手できるチケットの候補を出す | `references/github/fetch.md`「探す」 |
| 書き戻す | 書き換えたチケットを送る | `references/github/sync.md` |
| 状態を変える | 着手・レビュー中・マージ済み・手放す | `references/github/labels.md` |
| 閉じる | 完了・キャンセル | `references/github/close.md` |
| PR と紐づける | commit と PR 本文で紐づけ、確かめる | `references/github/pr.md` |
| 記録を残す | やめた方針と理由を残す | `references/github/record.md` |

**チケットの状態**（「取ってくる」が返す）：`open`（着手前・進行中）・`in-review`（PR が出ている）・`merged`（Base にマージ済みでリリース待ち）・`completed`（完了）・`canceled`（キャンセル済み）・`closed-completed`／`closed-not-planned`／`closed`（tixforge 以外の方法で閉じられた。完了として・予定なしとして・理由なし）。

**id は必ず `<scripts>/ticket-id.sh` で扱う**（手で 0 埋め・変換・解釈しない。シェルの算術に 0 埋めの数字を渡すと 8 進数になる）。出力はそのまま使う：

| 用途 | コマンド |
|------|----------|
| 引数からチケット id を取り出す | `bash <scripts>/ticket-id.sh detect "<引数>"` → `id: <id>`（無ければ `id: none`、形が不正なら `invalid: <語>`）と `rest: <id を除いた残り>`、番号が v2 の LT と重なれば `note: …`。明示的な形（`GT-…`・`#123`）は文中でも拾い、裸の数字は引数全体が数字のときだけ拾う |
| 指定された id の正規化 | `bash <scripts>/ticket-id.sh normalize <引数>`（`GT-000123`（大文字小文字は問わない）・`#123`・`123`（どれも issue 番号）） |
| そのチケットが実在するか | `bash <scripts>/ticket-id.sh exists <id>` → `issue`・`pull-request`（その番号は PR）・`none` |
| id → issue 番号 | `bash <scripts>/ticket-id.sh number <GT-id>` |

- **id のエラーを自分で直さない。** `normalize` が終了コード 2（桁数違い・形が不正）を返したり、`detect` が `invalid:` を返したりしたら、0 を補う・接頭辞を付けるなどして再実行しない。エラーをそのまま示し、正しい id をユーザーに尋ねる（桁の打ち間違いで別のチケットを指すのを防ぐための規則）。`detect` の `invalid: <語>` は、`bash <scripts>/ticket-id.sh normalize <語>` を実行してそのエラーを示す。`LT-` のエラーが移した先の `GT-` の id を示していれば、それで進めるか尋ねる。`normalize` の `注意:` と `detect` の `note:` は、示して、その issue でよいか尋ねる。
- 取り違えを防ぐため、dev・edit・cancel は始めるときに「`<id>`：<チケットのタイトル>」を必ずユーザーに示す。

| 用途 | パス |
|------|------|
| サービス／ドメイン知識 | `docs/context/**`（必要な分だけ読む） |
| tixforge 設定 | `.tixforge/config.yml`（チーム共通）・`.tixforge/config.local.yml`（個人の `language`・`gates`） |
| チケット | `.tixforge/<ticket-id>/snapshot.md` — dev が issue から取った版（「取ってくる」）。edit は `.tixforge/<ticket-id>/editing.md` で書き換え、書き戻したら消す |
| run の状態 | `.tixforge/<ticket-id>/state.md`（`<scripts>/run-state.sh` で作り、ヘッダを更新する） |
| ブランチ名 | `<ticket-id>-<slug>`（チケット id を接頭辞にする。slug は英小文字・数字・ハイフン） |

- プロジェクトの `.gitignore` は触らない（`.tixforge/` の中は `.tixforge/.gitignore` が git から外す）。
- PR 本文に書くのは、合意した方針の**結論と理由**（2〜3 行）だけにする。チケットや検討の過程にレビュアーが引っ張られず、実装そのものを見たレビューにするため。
- **言語**：チームで共有するものはドキュメント言語、本人だけが読むものは個人の言語で書く。どちらも無ければ日本語。
  - **ドキュメント言語**（`.tixforge/config.yml` の `language`）：チケット・`docs/context/**`・PR の本文とコメント（修正後の検証の結果）・issue のコメント（判断の記録・閉じるときのコメント）・GitHub に出る決まった文言。チケットと context は見出しもこの言語にする。PR のタイトルは、commit の件名と同じ決まりで書く（`skills/dev/pr.md`）。
  - **個人の言語**（「この人が使う値」の `language`）：会話（質問・説明・ゲートでの要約）・run の状態（`state.md`）の本文・Review の reviewer の報告。`state.md` の見出し・ヘッダ表のキー・`Verification @`・`PR comment @`・`PR head @` は英語の固定キーのまま。
  - `state.md` の内容を GitHub に出すとき（PR 本文の方針・受け入れ条件、判断の記録）は、そのまま貼らずにドキュメント言語で書き直す。
- **設定**（`.tixforge/config.yml`）のキー・値・無いときの扱い・書き方は `references/config.md` にある。キーの意味をユーザーに説明するとき、設定を書く・直すとき、キーが無いときに Read する。キーが無いときの既定：`gates` は `[plan, pr]`、`review.required` は `true`、`language` は日本語。「現在の状態」に「init が途中」があれば、`/tixforge:project init` 以外は、init で続けるよう案内して止まる（「移行が要る」もあれば update を先に通し、init はその後にする）。
- 上記パスは固定規約。`init` はこの規約どおりの雛形を作るだけで、パスの選択はしない。
- どのサブコマンドでも、既存ファイルを黙って上書きしない（`snapshot.md`・`editing.md` は issue から作り直すものなので例外。作り直すときは差分を示す）。
- **キャンセル済みのチケット**（チケットの状態が `canceled`、または `state.md` の `Status` が `canceled`）は、どのサブコマンドでも操作しない。その旨を伝えて止まる。

### スクリプト（`<scripts>/`）

結果が 1 つに決まる処理と、一字も変えずに写すべき処理はスクリプトに任せ、手で同じことをしない。出力は要約せずにそのまま使う。

| スクリプト | 用途 |
|------------|------|
| `ticket-id.sh` | id の取り出し・正規化・実在の確認・issue 番号への変換（上記） |
| `run-state.sh` | 状態ファイルの作成（`init`）、ヘッダの読み書き（`get` / `set`。`Status` の値を検査し、`Updated` も更新する）、前の版の形式からの更新（`migrate`） |
| `verify.sh` | 検証コマンドの実行と `Verification @ <hash>: …` の行の出力 |
| `review-input.sh` | Review の agent が読む入力（差分・commit 一覧・チケット・Approach・Plan と、共通の規則をつけた `index.md`）をファイルに書き出す |
| `pr-status.sh` | PR の状況（レビュー・CI・コンフリクト）の判定 |
| `issue-sync.sh` / `issue-label.sh` / `github-preflight.sh` | GitHub issue との同期・ラベルと担当者・事前チェック（`references/github/`） |
| `project-status.sh` | 設定と進行中の run の一覧（起動時に上の「現在の状態」へ自動で入る） |

## チケットを書く対話

チケットを作る・書き換える・取り込んだ issue を埋める・dev でチケットに書き戻すときは、どれもこの決まりで対話する。

- **中身はユーザーが書く。** Claude は項目ごとに質問し、答えを項目の形に整える。要件・受け入れ条件などの案を Claude から出すのは、ユーザーが「考えて」「案を出して」と頼んだときだけ。そのときも案は案として示し、合意したものだけ書く。ただし dev の Research で未決事項を片付けるときは、頼まれなくても調査の結果と推奨を示す（`skills/dev/run.md`。決めるのはユーザー）。
- 抜けている観点（エラーのとき・権限・空のとき・境界の値など）は、答えを書かずに「〜のときはどうしますか？」と**質問として**指摘してよい。答えは要件に書き、判定できる受け入れ条件にもする（ユーザーが挙げていない受け入れ条件を足したら、下書きでその項目を示す）。答えが「対象外」「まだ決めない」なら、対象外・未決事項に書く。
- **要件を捏造しない。** ユーザーが言っていないことは書かない。決まらない点は削らず「未決事項」に残す。
- 必要なら `docs/context/**` やコードを読んで、質問を具体的にする。

## 行動原則（全体を通して）

- 情報が不足・曖昧なときは**質問する**。存在しないファイルを勝手に作らない（チケットの中身は上の「チケットを書く対話」）。
- 一時ファイル（PR 本文・コメント・issue の下書きなど）は、`mktemp -d` で作ったディレクトリ（リポジトリの外）の中に新しいファイルとして書き、コマンドには絶対パスをそのまま書く（変数で渡さない。guard が本文を読めるように）。使い終えたらディレクトリごと消す。
- 仮定を置いて進めるときは**その仮定を明示**し、ユーザーが直せるようにする（該当セクションにも記録する）。
- 不要な手順や成果物だと感じたら、黙ってやらず（黙って省きもせず）**指摘する**。
- 懸念や反対は**理由付きで率直に**言う。ユーザーが提案したというだけで同意しない。

## ガードレール

- dev の 1 run につき 1 チケット。作業が別チケットの範囲に広がりそうなら指摘する。
- 明示的な確認なしに push / PR 作成 / マージをしない。tixforge は PR をマージしない。
- **hook（guard）が push・PR 作成・一部の git / gh 操作・Plan 承認前のコード編集に確認画面を出したり、ブロックしたりする。ブロックされたら、また確認画面で拒否されたら、コマンドを言い換えるなどして回避・再実行しない。** 理由（拒否なら拒否されたこと）をユーザーに伝えて指示を待つ。確認画面はチャットでの承認の代わりではない（PR フェーズでは、チャットで確認を得てから実行する）。
- 外部システムの操作は、チケットの GitHub issue に対する、`references/github/` に定めた操作だけにする。issue へのコメントも、そこに定めたものだけを、そこに定めた形で投稿する（確認を求めるものは確認を得てから）。tixforge はコメントを編集・削除しない。それ以外の外部システム（Jira など）にチケットを作らない。

## 扱わないもの

- GitHub issue 以外のチケット管理（Jira など）・複数ブランチにまたがる 1 チケット・バックログの管理（分解・優先度）。求められたら、tixforge では扱わないことを伝え、1 チケット 1 ブランチの範囲でできることを行う（大きいチケットは分けることを提案する）。
