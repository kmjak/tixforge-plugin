# Review の共通の規則

tixforge の review 系 agent が最初に読む。`review-input.sh` が、最初の `## ` からを `index.md` の末尾に書き出す（この行までは agent に渡らない）。

## 受け取るもの

このディレクトリのファイル（どれを読むかは agent ごとの指示に従う）：

- `diff.patch`：この run の差分
- `log.txt`：commit の一覧
- `files.txt`：変更されたファイルの一覧
- `delta.patch`：前のラウンドからの差分（2 ラウンド目以降だけ）
- `ticket.md`：チケット
- `approach.md`：合意済みの Approach（「未決事項の解決」の表を含む）
- `plan.md`：合意済みの Plan（「受け入れ条件 → 確かめ方」の対応表を含む）

呼び出し元からの指示：

- このディレクトリのパス
- 報告に使う言語
- 前のラウンドまでに「受け入れ」と決まった指摘とその理由
- 前のラウンドで「修正」と決まった指摘（2 ラウンド目以降）
- agent ごとの追加の入力（agent の「受け取るもの」）

足りないものがあれば、推測で補わずに「不足している入力」として報告の冒頭に書く。

## 進め方

まず `files.txt` と `log.txt` で変更の全体をつかむ。`diff.patch` が大きいときは、必要な範囲を区切って Read する。作業ツリーは実装後の状態なので、変更されたファイルや周辺のコードは、必要に応じて Read / Grep で読む。

- **1 ラウンド目**（`delta.patch` が無い）：agent の「やること」を、`diff.patch` 全体に対して行う。
- **2 ラウンド目以降**（`delta.patch` がある）：
  1. 前のラウンドで「修正」と決まった自分の指摘（自分のラベルの番号）が直っているかを確かめる。直っていなければ `[未修正]` として報告する。直っていれば報告しない。他の agent の指摘の修正と決まったものを直した変更は、合意外の変更などとして指摘しない。
  2. agent の「やること」を、`delta.patch` の変更（修正が持ち込んだ問題を含む）とその影響範囲に対して行う。それ以外の部分は前のラウンドで見ているので、新しく指摘しない。

## 守ること

- **読み取り専用。** このディレクトリのファイルとリポジトリのファイルを読むだけにする。
- `.tixforge/` 配下は読まない（実装者の作業記録で、それに引きずられずに判定するため。要るものはこのディレクトリにある）。
- 「受け入れ」済みの指摘は、同じ内容なら再び指摘しない。
- 命名・書式・好みの問題は指摘しない。
- 根拠の無い推測を事実として書かない。確信が持てない指摘は、消さずに「確度：低」として報告する。

## 報告の規則

- 指定された言語で、agent の「報告の形式」だけを返す（前置きや締めの文は不要）。ラベル（`[未実装]` など）と項目名（`重大度` など）も、その言語に訳す。
- 指摘が無ければ「指摘なし」とだけ書く。
- 重大なものから順に並べる。番号はラウンドごとに 1 から振る。
- `[未修正]` は、元の指摘と同じ項目で書き、前のラウンドの番号を添える（例：「前のラウンドの Q1 がまだ直っていない」）。重大度は元の指摘のものを引き継ぐ。

重大度：

- 高：完了と言えない（受け入れ条件を満たさない・データの損失・セキュリティの問題・主要な機能が動かない）
- 中：特定の条件で誤動作する、または合意と違う振る舞いになる
- 低：影響が小さい（まれにしか起きない・記録や手順だけのズレ）

確度：

- 高：どんな入力・状態で何が起きるか（またはどこがズレているか）を具体的に示し、コードで確かめた
- 中：道筋は示せるが、前提（呼び出し方・データ・合意の解釈）を確かめきれていない
- 低：具体的に書けない
